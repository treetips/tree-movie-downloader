# アプリ本体の更新確認と自己更新

## ステータス

- 承認済み (Accepted)

## 背景・課題

アプリ本体の更新確認は未実装で、About画面とタイトルバーには「更新確認は未実装です」と表示していた。
利用者は新しいバージョンが公開されても手動でダウンロードし直す必要があり、
配布物の `update-info.json` も生成していなかった。

一方、アプリは `.app` として配布し、起動時に外部ツールを取得する構成になっている。
アプリ本体の更新では、次の点を扱う必要がある。

- 最新バージョンの確認と、実行中バージョンとの比較
- 配布ZIPのダウンロード、SHA-256検証、展開、`.app` の置き換え、再起動
- 開発ビルドなど、実行中のアプリが配布物と一致しない場合の安全な扱い
- タイトルバー・About・メニューバーからの操作と、進捗・失敗の表示

## 決定

- GitHub Releases の最新リリースから `update-info.json` を取得する。
  - URL: `https://github.com/treetips/tree-movie-downloader/releases/latest/download/update-info.json`
  - 内容: `version` / `url` / `sha256`
- バージョンは `Major.Minor.Patch` のセマンティックバージョンで比較する。
  ビルド番号とプレリリース表記は現時点では扱わない。
- 起動時はバックグラウンドで確認し、ダイアログを出さず、更新がある場合だけ
  タイトルバー右端の更新エリアへ表示する。
- メニューバーの `Tree Movie Downloader` → `アップデートを確認` とAbout画面の
  ボタンから手動確認できる。手動確認の結果はダイアログと更新エリアへ反映し、
  確認失敗時は更新エリアを変更しない。
- 更新エリアは次の状態を持つ。
  - 更新あり: `アップデートが有ります`。クリックで確認ダイアログを開く。
  - インストール中: ダウンロードの確定バー、検証・展開・配置の不確定バー。
  - 失敗: 赤い表示と `再実行`。
  - 更新なし: 10秒で自動的に非表示。クリックでも閉じる。
- インストールは次の順で行う。
  1. 配布ZIPをダウンロードし、受信バイト数から進捗を表示する。
  2. SHA-256を検証する。
  3. `ditto` でZIPを展開する。
  4. 展開した `.app` を `codesign --verify` で検証する。
  5. 実行中の `.app` を退避し、新しい `.app` に置き換える。
  6. 新しいアプリを起動し、旧プロセスを終了する。
- 実行中のバイナリが `.app` の中に無い場合（`cargo run` など）は置き換えず、
  展開したアプリをFinderで表示して終了しない。
- インストール失敗時は理由を表示し、更新エリアの `再実行` からダウンロードをやり直せる。
- リリースワークフローは `.app` のZIP、`SHA256SUMS.txt`、`update-info.json`、
  `LICENSE`、`THIRD_PARTY_NOTICES.md` を同じReleaseに添付する。
- 外部ツールの配布（`tools-latest`）はpre-releaseのまま独立させ、
  GitHubの「Latest」がアプリ本体を指すようにする。

## 代替案

- Sparkleなどの更新フレームワークを導入する
  - 却下: 依存と設定が増え、現状の配布方法（GitHub ReleasesのZIP）に対して
    自前の実装で十分要件を満たせる。
- 手動ダウンロードだけを案内する
  - 却下: 更新確認とインストールの導線が無く、利用者の更新負担が大きい。
- 起動時に必ず更新ダイアログを表示する
  - 却下: 起動のたびに操作を中断させる。バックグラウンド確認とタイトルバーの通知に留める。
- 更新ZIPをアプリと同じ場所に展開して直接上書きする
  - 却下: 実行中のバイナリや署名の整合性が崩れる可能性がある。
    退避と置き換えを分け、失敗時に戻せるようにする。

## 結果

- アプリ本体の更新確認・ダウンロード・再起動までをアプリ内で完結できる。
- 更新がある場合だけタイトルバーに表示され、起動時の操作を妨げない。
- 開発ビルドでは自動置き換えを行わず、Finderで確認できる。
- 配布ZIPの検証と `.app` の署名検証により、壊れた更新を配置しにくくなる。
- 更新情報の生成はリリースワークフローに組み込まれるため、Release作成と同時に配布できる。
