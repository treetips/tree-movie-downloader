# アプリとライブラリの独立更新

- ステータス: Accepted
- 日付: 2026-11-26
- 更新通知の表示と操作配置は [ADR 0010](./0010-rex-style-update-status-pill.md) で置換
- アプリ更新後の再起動は [ADR 0020](./0020-user-initiated-app-relaunch.md) で置換

## 背景

アプリ本体は GitHub Releases の最新リリースにある `update-info.json` で配布情報を管理し、yt-dlp・ffmpeg・ffprobe は `tools-latest` の `tools-info.json` で管理している。両者の更新頻度と配布タイミングは異なるため、アプリ本体のリリースを待たずにライブラリだけを更新できる必要がある。

一方、起動時のツール準備は不足しているバイナリをそろえる処理であり、日常の更新確認とは別の責務である。ツールがそろっている起動でも更新確認は行う一方、見つかった更新を利用者の同意なしにインストールしない。手動確認では、片方の確認失敗によってもう片方の成功結果を失わず、利用可能な更新をまとめて扱う必要もある。

Release Tools は上流の更新がないたびに全プラットフォームの成果物を再公開していた。既存 manifest との比較を preflight に集約し、不要なビルド・公開を避ける必要がある。ただし、GitHub Releases へのアップロードは全件を atomic に置き換える処理ではないため、途中失敗時の部分更新も設計に含める必要がある。

## 決定

- アプリ本体とライブラリ（yt-dlp、ffmpeg/ffprobe）を独立した2種類の更新として管理する。更新の自動インストールは行わない。
- 起動時はアプリ本体をバックグラウンドで確認し、ツール準備が完了した後にライブラリも1回だけバックグラウンドで確認する。
- メニューと About からの手動確認はアプリとライブラリの両方を行い、結果を集約して1つのダイアログで通知する。片方の確認失敗時も、成功した側の更新情報・最新状態を保持する。
- タイトルバー右端の更新ボタン文言は、両方に更新がある場合は `アプリとライブラリの更新が有ります`、アプリのみの場合は `アプリの更新が有ります`、ライブラリのみの場合は `ライブラリの更新が有ります` に限定する。
- 更新ボタンは確認ダイアログを開き、利用可能な更新をまとめてインストールする。両方ある場合はライブラリ→アプリの順とし、アプリ更新の成功時に再起動する。ライブラリのみの更新では再起動しない。ライブラリの更新に失敗した場合はアプリ更新を開始しない。
- 更新は実行中のダウンロードを停止してから開始し、更新中はキューの新規開始・再開を禁止する。確認ダイアログは表示時点の更新計画を保持し、変化した場合は再確認する。
- ライブラリは `tools-info.json` の `version` / `platform` と `.installed.json` のローカル記録・バイナリの完全性を比較し、更新対象だけを SHA-256 検証して置換する。manifest schema と installed schema は変更しない。
- About 画面は `アプリ更新` と `ライブラリ更新` を分け、yt-dlp と ffmpeg のバージョンを表示する。
- Release Tools は preflight で上流の version / tag を1回解決し、既存 `tools-info.json` の全プラットフォームの version と一致すれば build / publish をスキップして正常終了する。`force=true` で再公開できる。manifest 欠落・不正・API 失敗は更新なしとせず、ワークフロー失敗として扱う。
- Release Tools の公開は全件 atomic ではないため、アップロード途中の失敗で一部のアセットだけが差し替わる可能性を明記する。

## 理由

アプリ本体とライブラリを分けることで、yt-dlp や ffmpeg の更新だけを迅速に配布でき、不要なアプリ再起動を避けられる。利用者の確認後にインストールすることで、通信やファイル置換を開始するタイミングを明示できる。

起動時の不足準備と日常更新確認を分離すると、ツールがそろっている場合も更新情報を確認できる一方、準備画面の通信理由を明確にできる。手動確認で成功結果を保持すれば、片側の障害が他側の更新情報を誤って消すこともない。

全プラットフォームの manifest を比較することで、1プラットフォームだけ古い状態でも公開をスキップせず、配布物の一貫性を保てる。manifest 欠落や API 失敗を正常終了させると更新を見逃すため、明示的な失敗として検知する。

## 結果

- ライブラリだけを更新してもアプリは再起動せず、両方を更新する場合もライブラリの成功を確認してからアプリを置き換える。
- ツールがそろっている通常起動でも更新確認のための通信は発生するが、ツール準備画面は表示されない。
- 既存の `schemaVersion: 1` を維持するため、配布物とローカル記録の互換性を保てる。
- Release Tools は上流が同じ場合は成果物を再生成せず正常終了し、明示的な `force=true` でのみ再公開する。
- 公開途中の失敗後は一部だけ新しくなった状態が残り得る。原因を修正して `force=true` で Release Tools を再実行し、全アセットと `tools-info.json` の一致を確認する必要がある。
